# 网页启动与体积预算

这一页回答两个可量化的问题：**打开页面要多久**，以及**发布包有多大、什么时候才去读那些大文件**。数据由 `node scripts/measure-web-startup.mjs` 在真实（无头）浏览器里测出来，写进[启动与体积数据](data/web_startup_budget.json)，再由 `npm run check-web-startup-budget` 固定。

| --- | --- | --- |

| 首次内容绘制 | 445 ms | 265 ms |
| 画布就绪 | 223 ms | 81 ms |
| 模型标签不再显示“加载中” | 356 ms | 196 ms |
| 提示“资源缓存已完成” | 479 ms | 263 ms |

**首屏现在多了一块 1.16 MB，这是有意的**：默认视图显示的不再是自建的示意骨架，而是从 RajagopalLaiUhlrich2023 导出的真骨骼，所以那块 `models/full_body_skeleton.glb`（1,171,520 字节）会随首屏一起取下——这就是冷启动传输从 42,961 字节涨到 1,207,709 字节的全部原因。换来的是默认视图里 22 体段骨骼几何（11 块骨网格覆盖躯干与四肢）不再是示意形状。**其余大文件仍然不在首屏路径上**：10.7 MB 的解剖模型与两份 1.6 MB 的上肢参考数据都只在用户切到对应视图时才取，检查里那条断言仍然钉着——冷启动的资源列表必须**没有** `z_anatomy_reference.glb`，且必须有 `prototype_parts.glb`。如果哪天要把这块骨骼也移出首屏，办法是等用户第一次打开骨骼显示再取；本轮没有这么做，因为默认视图本来就显示骨骼。

**刷新不再下载任何字节**：Service Worker 在首次安装时把整份清单写进缓存，之后刷新由缓存提供，测量到的传输量为 0。这也是“离线可打开”的量化版本；**真的断网能不能打开**由 `npm run check:ui-offline` 在真实浏览器里验收（见下）。

## 断网之后真的还能用吗

`npm run check:ui-offline` 把生产构建装进真实浏览器，等离线包通过完整性核对后**用 DevTools 协议把网络关掉**（页面里的 `navigator.onLine` 也会变为假），再刷新并走一遍用户会走的路。它验证 9 件事：离线包被核对为完整；断网刷新仍能启动且由 Service Worker 接管；默认示意模型渲染出来且画布有尺寸；深蹲、卧推、实力举三个动作各自的 OpenSim 参考视图都能在断网下到达“已加载”的措辞；10.7 MB 的解剖研究层能在断网下加载；三份参考数据确实都在 Service Worker 的缓存里（逐个 `caches.match` 读出版本号）；**没有任何打包资源再被应用向服务器索取**；恢复联网后退回“资源缓存已完成”；页面全程没有未捕获错误。

**关掉浏览器网络还不够。** DevTools 的关网拦不住 Service Worker 自己的 `fetch()`：worker 仍可能替页面把缺失的资源从本机服务器取回来。因此检查把**本地测试服务器**当成断网声明的执法点——离线包核对完整之后，服务器立刻改为拒绝并记录每一个请求（`503` + 计数），再断言没有任何 `/data/`、`/models/`、`/icons/`、`/assets/` 或清单请求到达过它。仍会到达服务器的只有三类并都有理由：浏览器对 `/sw.js` 的版本更新检查、worker 对 `/` 的网络优先导航尝试（失败后回落到缓存）、以及不属于打包内容的站点 `favicon.ico` 探测。

这条检查做过负向验证：把 `bench_tsm_reference.json` 从 Service Worker 的预缓存清单里删掉并重新构建后，检查会在“三个动作都能在断网下加载参考数据”这一步**超时失败**；在加固之前，同样的负向操作曾经**假通过**，因为 worker 把数据从服务器取回来了（见[阶段总结](项目阶段总结.md) 增补之十九）。

## “资源缓存已完成”现在是真的

测量这一页时发现了一个界面诚实问题：Service Worker 以前只回答**缓存名**（`{cache: ...}`），页面就把头部状态改成“资源缓存已完成”。缓存名对得上并不代表内容完整——浏览器在存储紧张时可能清掉一部分条目，或者某次预缓存中断过。现在：

- 安装阶段只有在 `cache.addAll(...)` **全部成功之后**才把清单写进缓存（`/__precache-manifest.json`）；
- 页面询问时，Service Worker 逐项核对清单里的每个 URL 是否真的在缓存里，回答 `{complete, entries, expected, missing}`；
- 页面据此显示“资源缓存已完成”，否则显示“离线包未就绪 · 缺 N 项”，原来那句只在注册失败时出现的提示不再被用来掩盖部分缺失。

这行状态现在还说清**当前有没有网络**：设备断网时显示“离线 · 资源缓存已完成”（或“离线 · 离线包未就绪”），恢复联网后自动退回“资源缓存已完成”。健身房里没信号时用户能一眼看出这是正常的离线状态，而不是加载失败。

`npm run check:offline-cache` 除了原有的离线读取，现在还会问这个状态两次：**完整时**必须回答 `complete: true` 且 `missing` 为空；**故意删掉一个资产后**必须回答 `complete: false` 并点名缺了哪个文件，删掉清单本身同理。也就是说，界面不会再声称一件没做到的事。

## 怎么复测

```powershell
npm run build                     # 先产出 dist/
node scripts/measure-web-startup.mjs   # 重新测量并覆写 docs/data/web_startup_budget.json
npm run check-web-startup-budget       # 固定体积与预算
```

## 预算

检查里写死的上限（当前值远低于它们，只用来拦住“明显变慢／变大”）：内嵌首页 ≤ 1,600,000 字节、`dist/` 总量 ≤ 40,000,000 字节、首次内容绘制 ≤ 3,000 ms、模型就绪 ≤ 30,000 ms、刷新后模型就绪 ≤ 10,000 ms。

## 这些数字不能说明什么

- 这是**桌面无头浏览器**在同机 localhost 上的**单次采样**，不是手机、不是健身房现场，也不是多次统计的平均值。它只能排除“明显变慢”这类回归，不能当作启动速度验收；真机启动与 390 px 下的实际手感仍未验收（没有设备）。
- 计时含本机文件读取与无头浏览器的首次渲染，绝对值受机器负载影响；比较不同版本应在同一台机器、同一次运行里对照。
- 冷启动的“页面自身下载量”由同机 localhost 提供，不含网络往返、TLS、CDN 或移动网络开销；真机首装体积还要加上 APK 自身（见[安卓构建](安卓构建.md)）。
- “模型就绪”以界面标签不再显示“加载中”为准，表示骨骼／肌肉网格已经挂上，不表示首帧已经绘制完成。
- 只测量默认深蹲视图；切到卧推、实力举或研究叠加层会另外加载参考数据，这里没有覆盖，因此上表的“首屏很快”不等于“每个视图都快”。
